# 任务书 · d1-ime-win32-recon（IME 缺陷源码定位与修复方案）

## ⚠️ 先读这段，它决定你能做什么、不能做什么

**本机是 headless Linux（无图形界面、无 Windows、无中文输入法）。**

所以：**你无法复现任何 Windows IME 行为。不要尝试。**

历史教训：上一轮有卡在这里耗了 61 轮、零产物、整轮作废 —— 因为它反复尝试编译 GUI 探针、
在 Linux 上找 Windows 输入法、在无关目录里翻源码。

**本卡唯一产出是一份 md 文档。不做实验，不跑 GUI，不编译探针。**
只在已下载的源码里做静态阅读与定位，然后写方案。

## 本卡定位：**纯静态源码分析（只读，不编码，不实验）**

## 背景

本仓用 GPUI + gpui-kit 做桌面界面。GPUI 在 Windows 上有一条中文输入法硬缺陷，
是中文产品的阻塞项（主界面会话输入框必须能打中文）。

已知两条 Zed issue：

| Issue | 症状 |
|---|---|
| zed-industries/zed **#56327** | `WM_KEYDOWN` 路径不检查 IME 组合态 → 汉字重复插入；另有 `direct_write.rs` 多字节切片 panic |
| zed-industries/zed **#64850** | IME 定位只给一个点（`y = origin.y + height/2`）+ `CFS_CANDIDATEPOS` 无排除区 → 候选框盖住正在输入的字 |

## 源码在哪（直接用，别自己找）

依赖已经拉好了，源码就在本机 registry：

```
~/.cargo/registry/src/rsproxy.cn-e3de039b2554c837/
├── gpui-pre-0.3.9/          ← 上游 gpui 的核心（协议、元素、文本系统）
├── gpui-pre-linux-0.3.9/    ← Linux 平台层
├── gpui-pre-platform-0.3.9/ ← 平台抽象接口
├── gpui-base-0.8.0/         ← gpui-kit 的基础层（含 input/base/state.rs）
├── gpui-component-0.8.0/    ← 输入框等组件
└── gpui-kit-0.8.0/          ← 基座入口
```

**注意**：Windows 平台层的 crate 可能**不在**上面这个目录里（Linux 上不会下载 Windows 目标）。
先 `ls` 确认：

```bash
ls ~/.cargo/registry/src/rsproxy.cn-e3de039b2554c837/ | grep -i "gpui"
```

- **若 Windows 平台 crate 存在**：直接读它，找 `WM_IME` / `ImmSetCandidateWindow` / `CFS_CANDIDATEPOS`。
- **若不存在**：从 GitHub 读（**只读网页，不 clone**）：
  `https://raw.githubusercontent.com/zed-industries/zed/<commit>/crates/gpui/src/platform/windows/`
  gpui-kit 用的 commit 记在 `gpui-pre-0.3.9/.cargo_vcs_info.json`；若没有就查 gpui-kit README。
- 两条路都失败 → **如实写「Windows 平台源码不可获取」并结束**，不要继续在别的目录里乱翻。

## 你要做的事（只有两件）

### 1. 源码定位（找位置，不改代码）

对下面每个关注点，找到 **文件路径 + 行号 + 代码原文片段**，并说明它现在错在哪：

| # | 关注点 | 搜索关键词 |
|---|---|---|
| 1 | `WM_KEYDOWN` 处理是否检查 IME 组合态 | `WM_KEYDOWN`、`WM_CHAR`、`handle_keydown`、`parse_char_message` |
| 2 | IME 候选框定位用的矩形 | `ImmSetCandidateWindow`、`CFS_CANDIDATEPOS`、`CFS_EXCLUDE`、`rcArea`、`COMPOSITIONFORM` |
| 3 | 多字节字符切片 | `direct_write`、`TextRun`、按字节切 `&str` 的地方 |
| 4 | 应用层能否拿到 caret 矩形（决定修法可行性） | `caret`、`bounds`、`element_bounds`、`window_bounds` |

第 4 项特别重要：**如果应用层拿不到光标矩形，那修复方案就落不了地。** 这条要明确给结论。

### 2. 写修复方案（核心产出）

对每条缺陷给一张表：

| 项 | 要求 |
|---|---|
| 根因 | 一句话说清「为什么会这样」，附源码位置 |
| 修法 | 具体到改哪个函数、加什么判断。IME 定位那条正解方向是 `CFS_EXCLUDE` + `rcArea` 传 caret 矩形（不是单点） |
| 改动面 | 预计改哪些文件、多少行 |
| 风险 | 可能影响什么（输入法兼容性、其他平台） |
| 验证方法 | 改完**怎么证明修好了**（可执行、可复现的步骤；在 Windows 机器上能执行） |

### 3. 判断：修在哪（三选一，给推荐 + 理由）

| 选项 | 说明 |
|---|---|
| A. vendored 本地 gpui 源码 | 完全掌控，但与上游脱节、升级要手工 rebase |
| B. fork gpui-kit 并向上游 PR | 社区共享，但依赖对方合并节奏 |
| C. 应用层绕过（WebView 承载输入框） | 不改底层，但 WebView 使用面积已限定 |
