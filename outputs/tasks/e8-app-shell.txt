# 任务书 · e8-app-shell（应用入口组装）

## 本卡定位：**把所有接线层组装成可运行的应用**（最后一张，依赖 e1–e7 全部合入）

上一批的 `ui/gpui_app.rs` 只有一个 `SkeletonView`（标题 + 输入框）。
本卡把它升级成**真正的工作台**：三区布局 + 全部视图。

## 你要做的事

### 1. 组装根视图（改 `ui/gpui_app.rs`）

根视图结构：

```
┌──────────────────────────────────────────────┐
│ 标题栏（WINDOW_TITLE）                        │
├──────────┬──────────────────────┬────────────┤
│          │                      │            │
│ Sidebar  │   SessionStream      │ RightPanel │
│ ViewGpui │   (会话流)            │ ViewGpui   │
│          │                      │            │
├──────────┴──────────────────────┴────────────┤
│ InputAreaGpui（输入区横跨中右两列下方）          │
└──────────────────────────────────────────────┘
```

- 宽度用 `ui/layout.rs` 的 `SidebarLayout` / `RightPanelLayout`（边栏 260px 默认，可拖拽调宽可后置）
- **命令面板**：快捷键触发，浮在最上层（`ui/palette_gpui`）
- 环境 / 组织视图**暂不进主界面**（e1-e4 只做工作台四件），但代码要编译进去

### 2. 二进制入口（改 `src/bin/lengsuo-desktop.rs`）

现在是一个占位 `fn main() {}`。改成：

```rust
#![cfg(feature = "ui")]  // 或在 main 里判断，未开 feature 时打印提示退出
fn main() {
    // 调 ui::gpui_app::launch()（组装后的新版本）
    // 失败时 eprintln + 非零退出码
}
```

`Cargo.toml` 的 `[[bin]] required-features = ["ui"]` 已由主理人落好，**不要改 Cargo.toml**。

### 3. Linux headless 行为

47 是无显示服务器环境。`launch()` 已处理：窗口创建失败会返回 `LaunchError::Window` 而不是卡死。
**保持这个行为**，并在报告里记录 Linux 下运行的实际输出（应为报错退出而非 panic）。

## 硬约束

- **不改** `Cargo.toml`、`ui/mod.rs`、`src/state/**`、`src/theme/**`
- **不改** e1–e7 产出的 `*_gpui.rs`（它们已验收；有 bug 报告里写）
- 根视图**不持有任何业务语义**：数据全部来自 state 层的 demo 构造

## ⛔ 执行纪律（本批新增，违反即作废）

**上一批 e4/e5/e6/e7 四张卡全部作废**：它们把 45 次工具调用预算全花在调研
gpui-kit 的 API 上，一行代码没写就撞上限，退出码却是 0 —— 台账因此误标成
"已合入"，产物静默丢失（4 张卡的工作全部白做）。

**e1/e2 也不行**：写完 259 / 595 行但一次都没编译过，留了 15 / 16 个编译错误。

### 规则 1：调研预算 ≤ 12 次调用

查 gpui-kit API 的工具调用**最多 12 次**，用完就必须开始写代码。

不需要提前把 API 查全 —— 编译器会告诉你缺什么。**先写一个能编译的最小版本，
再按报错补**。这比先调研后实现快一个数量级。

### 规则 2：增量编译，每 5-10 分钟必查一次

**每写完一个渲染分支，立刻跑一次**：

```bash
cargo check -p lengsuo-desktop --features ui
```

⚠️ 首次编译约 1-2 分钟（gpui 依赖已编译好，之后 10-30 秒）。
**不要攒到最后才编译** —— 上批 e1/e2 就是攒到最后，16 个错误一起爆，预算耗尽。

### 规则 3：先落最简可编译版本

顺序固定：

1. 写最小骨架（一个 `impl Render` + 一个 `div()`，先保证能编译）
2. 立刻 `cargo check` 确认
3. 逐个加渲染分支，**每加一个就 check**
4. 最后补测试与文档

**任何时候预算即将耗尽，就把当前能编译的版本提交下来** ——
宁可交一个 60 分但能编译的版本，也不要交一个 95 分但编不过的版本。
空改动（没写任何代码）等于这张卡白跑，会被 verify 判失败。

### 规则 4：verify 会拒绝空改动

主理人已修 `card_guard.verify`：**改动文件数为 0 直接判失败**，
`HEAD` 未领先 base 也判失败。所以「调研到底、一行没写」是必然作废的，
不要再试图这样交差。
