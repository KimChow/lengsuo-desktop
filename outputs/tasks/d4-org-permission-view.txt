# 任务书 · d4-org-permission-view（组织域 + 权限可见性视图）

## 目标

实现**企业管理**的界面层：部门 / 成员 / 角色 / 权限可见性。
这是对标端语义的核心，你上一批决策已定「走对标端那一套（人 + 环境资源分配）」。

## 权威约束（逐条遵守，这是本卡最重要的部分）

### 约束 1：界面不判定权限

这是硬规则，源自服务端契约的明确要求：

> 权限以服务端按「公司 + 角色 + 资源关系」权威计算，**前端入口可见与禁用不构成授权证据**。
> UI 禁用 ≠ 后端拒绝，后端必须独立校验。

所以本卡**只做一件事**：把服务端下发的**可见性标记**渲染出来。
**禁止**写这类代码：

```rust
// ❌ 禁止：界面自己推理权限
if user.roles.contains("admin") { show_delete_button() }
```

**允许**的写法：

```rust
// ✅ 正确：只读服务端给的标记
if item.get("can_delete").and_then(|v| v.as_bool()).unwrap_or(false) { ... }
```

注意 `unwrap_or(false)` —— **拿不到标记时默认不可用**（fail-closed）。

### 约束 2：双轨独立，拒绝原因要分开

服务端契约定了双轨模型：

```
effective(feature) = entitled(company, feature) AND permitted(member, feature.code)
```

拒绝原因必须**分原因展示**，不能混为一种「无权限」：

| 原因码 | 界面文案 | 引导路径 |
|---|---|---|
| `NO_ENTITLEMENT` | 当前套餐不包含此功能 | → 升级购买 |
| `NO_PERMISSION` | 你没有该操作权限 | → 申请权限 |
| 策略拒绝 | 该操作已被企业策略禁止 | → 无自助路径，提示联系管理员 |

**第三种不接申请入口** —— 它由企业策略权威裁决，不设自助路径。

### 约束 3：三类状态严格区分

服务端契约明确要求：

> 查询错误、真实空集与无权限**三态分离**。

**先读** `src/state/org.rs` —— 它已经实现了这个约定（`should_show_empty_state()`），
本卡要复用它，不要另造一套。

## 既有资产

`src/state/org.rs` 有 `OrgListState`：成员/角色/部门共用的列表状态。
包含三态区分、选中项管理、「失败态不显示空态」的判定。

## 你要做的事

### 1. 扩展状态层

在 `src/state/` 下新建 `org_perm.rs`（或类似）：

- 定义一个「能力标记」结构，承载服务端下发的 `can_*` 布尔标记
- 实现 `effective()` 的界面侧表示：**只读服务端结果，不自己 AND 运算**
- 实现拒绝原因枚举：`NoEntitlement` / `NoPermission` / `PolicyDenied`
- **缺失标记时默认不可用**（fail-closed），并写测试证明这一点

### 2. 实现视图

在 `src/ui/` 下新建组织域视图：

- 部门树渲染（层级展示）
- 成员列表（复用 `OrgListState`）
- 角色列表（含 `preset_key` / `is_builtin` / `is_ai_assistant` 三字段的展示）
- 按能力标记控制按钮的可用/禁用状态

### 3. 特殊规则

- **`ai_assistant` 角色全局只读**：禁编辑、禁删除（服务端强制，界面也要如实反映）
- 拒绝时**分原因**展示文案与引导，不混为一种
